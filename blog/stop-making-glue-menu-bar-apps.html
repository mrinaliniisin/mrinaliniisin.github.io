Stop making glue Menu Bar Apps!

July 16, 2026

A lot — most single-purpose "glue" utilities are basically a Hammerspoon script wearing an app costume. The dividing line is UI complexity and how deep into the OS they reach.

Trivially replaceable (Hammerspoon exposes the exact API):

  • Window managers — Rectangle/Magnet → hs.window, hs.grid. This is Hammerspoon's home turf.
  • Caffeine-style "keep awake" → hs.caffeinate.
  • Hotkey launchers / app switchers → hs.hotkey, hs.application.
  • Clipboard-history-lite, text expanders → hs.pasteboard, hs.eventtap.
  • "Show battery %/wifi/CPU/weather in the bar" → hs.menubar + a timer + hs.http.
  • Auto-switch behavior on events (mute mic when a certain app opens, run a script when you join a wifi, remap keys per-app) → the various hs.*.watcher modules.

The reason these collapse into a script: they're event → action with a tiny bit of state. That's ~10-40 lines. The commercial app is mostly a preferences GUI and an icon wrapped around the same handful of system calls Hammerspoon already binds.

Awkward but doable — anything needing real UI. Hammerspoon can draw (hs.canvas, hs.webview, hs.chooser), but you're hand-rolling it. Alfred/Raycast's core (fuzzy launcher) is a hs.chooser; their value is the polished UI, plugin marketplace, and preference panes — the long tail, not the mechanism.

Not replaceable — these need capabilities Hammerspoon doesn't (and shouldn't) have:

  • Anything with a system/kernel extension: VPNs, Little Snitch (network filter), Karabiner's low-level keyboard driver, virtual audio devices (Loopback).
  • Menu-bar frontends to a background daemon/service: Docker, Dropbox, a password manager's vault.
  • Real-time media, screen recording pipelines, GPU stuff.

The mental model: Hammerspoon is a userland scripting layer over the public macOS automation APIs. If an app's job is orchestrating those public APIs, it's a script. If it needs privileged/kernel access or ships its own daemon, it isn't.

Your Clojure instinct is the right one here: these utilities are pure glue code, and glue code doesn't need to be an application — it wants to be a few functions in a running REPL, which is exactly what your init.lua is. The friction Hammerspoon doesn't solve is distribution and a settings GUI for non-programmers — which is precisely why the commercial versions exist.
